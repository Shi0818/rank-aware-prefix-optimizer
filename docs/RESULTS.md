# Results — paired A/B, 100 queries

Everything below comes from `results/*.csv`, which is generated by
`tools/make_results_tables.py`. Per-query pairing: both arms run the **same query**,
the **same target**, the **same initial prefix** and the **same seed**, so the
comparison is a paired test rather than two independent samples.

## Setup

| item | value |
|---|---|
| dataset | IMDB name profiles (`title.basics` / `name.basics`), 1,000-passage retrieval corpus |
| embedder | `Salesforce/SFR-Embedding-Mistral`, fp16, frozen, last-token pooling |
| queries | 100, ids **208–307** (`--start 208 --end 308`) |
| search | 500 iterations cap, prefix length 10, top-k = 10 |
| seed | `20261008 + i` per query, identical across arms |
| judging | official `check_success` (faiss/HNSW top-10), **bare-query** convention |
| baseline arm | released `DGD.py` objective, run on the same queries (historical run) |

**Strict success** = the target passage reaches rank 1 **and** the correct passage
leaves the top-10.

---

## 1. Headline

| metric | released optimizer | rank-aware optimizer | change |
|---|---|---|---|
| **strict success** | 15/100 = 15.0 % | **72/100 = 72.0 %** | **+57.0 pt** |
| correct passage evicted from top-10 | 15.0 % | 73.0 % | +58.0 pt |
| target reaches rank 1 | 95.0 % | 90.0 % | −5.0 pt |
| median rank of correct passage (capped at 11) | 2 | 11 | +9 |
| median cosine of correct passage (before → after) | 0.7505 | 0.6089 | −0.1416 |

No query was already a strict success before the attack, so the comparison is not
diluted by queries that needed no optimisation.

### Per-query flips

| category | queries |
|---|---|
| **fail → success** | **57** |
| success → fail | **0** |
| both succeed | 15 |
| both fail | 28 |

A clean gain: 57 flips up, none down.

## 2. Stratified by the target's rank before the attack

| group | n | released, strict success | rank-aware, strict success | target lost rank 1 |
|---|---|---|---|---|
| target already rank 1 | 62 | 15 (24.2 %) | 53 (85.5 %) | **0** |
| target not rank 1 | 38 | 0 (0.0 %) | 19 (50.0 %) | **10** |

Two facts worth keeping:

* **67 % of the gain (38/57) needs nothing but eviction** — the target already held
  rank 1, so the whole improvement comes from pushing the correct passage out. This is
  the side of the metric the released objective does not optimise directly.
* **All 10 queries that lose rank 1 are in the second group.** Of the 62 queries whose
  target already held rank 1, not a single one lost it. Losing rank 1 is therefore
  predicted by one binary condition, not by how large the initial cosine gap was (the
  gap distributions of the flipped and non-flipped subsets overlap heavily).

Queries that lose rank 1: `210 219 221 235 249 269 277 282 297 302`.

---

## 3. Why the two groups behave differently

The target term is a hinge, `relu(tau - cos_target)` with a **fixed** `tau = 0.90`.
It asks for an absolute cosine level, not for "the target beats whoever is currently
rank 1". In group A the target is already rank 1, so the hinge is already satisfied and
contributes no gradient — the search is free to spend everything on eviction. In group
B the target first has to climb, and the two terms compete.

The 10 failures are the visible cost of that design choice, and they fail in a
characteristic way: both cosines drift down together while the *order* between target
and correct passage barely changes (query 210: `cos_target` −0.146, `cos_correct`
−0.153; the gap ends at +0.018, essentially where it started). See
`docs/METHOD.md` §4 for the fix (a ranking margin instead of a fixed threshold).

## 4. Judging-convention side note

The same optimized prefixes were re-judged under the upstream convention
(Instruct-wrapped query, ~25 extra tokens):

| convention | strict success |
|---|---|
| bare query (reported) | 72/100 = 72.0 % |
| Instruct-wrapped query (upstream default) | 4/100 = 4.0 % |

This ~18× gap is a property of the embedding model's sensitivity to the wrapper, not of
the optimizer — but it means **any success rate for this attack is only interpretable
together with the judging convention**. Both arms are judged identically here, so the
*difference* of +57 pt is unaffected.

## 6. Known boundary cases

**Rank conventions disagree on 2 of 100 queries** (`query 232` and `query 305`):

* `232` — under exact corpus-wide cosine the correct passage is at rank 16 (evicted) and
  the target at rank 1, but the official faiss/HNSW judge returns a different passage at
  `topk[0]`, so `check_success` reports a non-success. Exact-cosine eviction count is
  73 while strict success is 72; this query is the difference.
* `305` — the search stopped at iteration 18 believing the criterion was met (internal
  exact-cosine rank of the correct passage = 11), but the official judge places it at
  exactly 10, i.e. still inside the top-10.

Both are boundary effects of comparing an *exact* ranking against an *approximate*
(HNSW) one. **Report strict success with the official judge**; the exact-cosine ranks
are diagnostic only. Do not mix the two in one number.
